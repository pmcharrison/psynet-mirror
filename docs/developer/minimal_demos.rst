Minimal demo migration
======================

Goal
----

PsyNet's long-term goal is for all demos to use a *minimal* repository layout.
In this layout each demo keeps its authored experiment files together with
``README.md``, ``requirements.txt``, and ``constraints.txt``, while standard
boilerplate (for example ``Dockerfile``, ``test.py``, ``config.txt``, and the
``docker/`` helper directory) is regenerated on demand with ``psynet scaffold``.

This reduces duplication in the repository while preserving the user workflow of
copying a demo into a new workspace and getting started quickly.

Current status
--------------

At present only two pilot demos use the minimal layout:

- ``demos/features/api``
- ``demos/experiments/vocabulary_test``

We do **not** plan to migrate the remaining demos until the approach has received
external code review. The repository should therefore remain in a mixed state for now:
pilot demos are minimal, the rest still keep the full boilerplate layout.

The demo update tooling now detects this from the demo directory itself rather than
from a hand-maintained pilot manifest: if a demo is already minimal, updates preserve
that layout automatically.

Target file policy
------------------

Keep in each demo:

- ``experiment.py``
- ``requirements.txt``
- ``constraints.txt`` (for now)
- demo-specific helper modules, templates, static files, and assets
- a short, demo-specific ``README.md``

Generate on demand with ``psynet scaffold``:

- ``.gitignore``
- ``.dockerignore``
- ``Dockerfile``
- ``config.txt``
- ``test.py``
- ``pytest.ini``
- ``AGENTS.md``
- ``.python-version``
- ``Dockertag``
- ``.github/workflows/test.yml``
- ``.vscode/launch.json``
- ``docker/``

Why ``constraints.txt`` stays
-----------------------------

Even though ``constraints.txt`` looks autogenerated, we keep it for now because it
still serves as the documented installation and reproducibility path for demos.
Any follow-up change to remove demo ``constraints.txt`` files should be handled as
its own migration once the minimal-layout change has settled.

Pre-review tasks
----------------

Before the repo-wide migration, we want the following tooling and evidence in place:

1. A non-destructive audit command that reports what would be removed from each
   demo and flags cases needing manual review.
2. A round-trip validation harness that copies representative demos to temporary
   directories, prunes them to the minimal layout in the copy, runs
   ``psynet scaffold``, and checks that they still work.
3. Clear user-facing README wording for minimal demos.
4. External review of the overall migration strategy before mass deletion.

Audit workflow
--------------

Use the audit script to inspect the current demo tree without modifying it:

.. code-block:: bash

   python demos/audit_minimal_demos.py

Useful variants:

.. code-block:: bash

   python demos/audit_minimal_demos.py --only-nonminimal
   python demos/audit_minimal_demos.py --demo demos/features/api
   python demos/audit_minimal_demos.py --json

The script reports, for each demo:

- whether it is already minimal
- which scaffold-managed paths would be removed
- which preserved paths would remain
- whether the README still matches the generic template
- whether scaffold-managed files or directories appear to be customized

Validation workflow
-------------------

Representative round-trip validation lives in the test suite. It works by copying
selected demos to temporary directories, pruning scaffold-managed files from the
copy, regenerating them with ``psynet scaffold``, and checking that authored files
are unchanged. Selected demos are also exercised with ``psynet test local`` after
the round trip, and relative-import demos are included to ensure that removing
``__init__.py`` from minimal demos does not change import behavior.

Run the targeted validation with:

.. code-block:: bash

   python -m pytest tests/isolated/test_minimal_demo_roundtrip.py -q

Migration after review
----------------------

Once external review is complete, the intended repo-wide migration is:

1. Remove scaffold-managed boilerplate from every demo.
2. Rewrite remaining generic READMEs to the minimal-demo template.
3. Simplify demo-update tooling so minimal demos are the default rather than an
   opt-in pilot.
4. Re-run the audit and round-trip validation checks.

The mass migration should be scripted and reviewable, not done by hand.
